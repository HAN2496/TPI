03. LOEO 실험 실행 안내

작성 2026-09-30 · 코드: run_loeo.py, reward/fully_bayesian/loeo/ · 근거: 01, 02 · 대상 논문 절: Section VI (Experiments)

1. 무엇을 계산하는가

적격 평가자 전원을 한 명씩 held-out하는 leave-one-evaluator-out(LOEO) 프로토콜이다. 한 폴드에서 하는 일은 다음과 같다.

  1. 뱅크 정리. population 평가자 에피소드에서 전체 후보 뱅크를 계산하고, 채널 안에서 |r| 0.95 이상 쌍을 우선순위 규칙으로 제거한다.
  2. 기준 모형 적합. 정리된 뱅크로 공유 spike-and-slab 계층 모형을 Gibbs로 적합한다. 시드마다 반복한다.
  3. Held-out 평가. 평가자의 에피소드를 시간순으로 앞 절반(문맥)과 뒤 절반(holdout)으로 나눈다. 예산 t = 0, 5, 10, 20, 최종(문맥 전체)에서 문맥 앞 t개로 개인화하고 holdout에서 지표를 계산한다. 작은 예산은 시작 오프셋 3개로 평균한다.
  4. 지표. MLPD와 ELPD, Brier, AUROC, AUPRC, ECE, calibration slope와 intercept, epistemic과 aleatoric 평균, 두 성분의 Spearman 상관, epistemic으로 정답 여부를 예측하는 AUROC, risk-coverage AURC와 E-AURC, posterior x bootstrap AUROC 신뢰 구간과 신뢰 판정.
  5. 비교 모형. HB-full(포함 사전분포 없음), EB-MAP(Laplace 근사 particle), pooled 로지스틱, independent 로지스틱, 선택 시 GBT.
  6. 부가 산출. 기준 모형의 피처 역할표(PIP, q_j, S_j, 공통/개인/비활성), 센서 단위 PIP, prequential 누적 log score.

select 스테이지는 폴드마다 projpred forward 경로를 만들고, 경로 위의 크기 후보(1, 2, ..., 40, 전체)와 PIP 1/2 이상 집합을 열 부분집합으로 재적합(축소 Gibbs)해 held-out MLPD를 낸다. 리포트에서 폴드 평균과 전체 대비 paired 차이의 SE로 one-SE 규칙을 적용해 크기를 고르고, 폴드별 선택 집합의 Nogueira 안정성을 계산한다. sensors 스테이지는 5채널의 31개 비공 부분집합 각각을 같은 방식으로 재적합해 MLPD 표와 leave-one-sensor-out 요약을 만든다.

2. 실행 명령

저장소 루트에서 실행한다. Windows 데스크톱은 README 관례대로 .venv\Scripts\python.exe를 쓴다.

2.1 먼저 합성 데이터로 배선 확인 (1분 내)

.venv\Scripts\python.exe run_loeo.py --data synthetic --fast --stage all

끝나면 outputs/loeo/<timestamp>/report/에 main.md, select.md, sensors.md와 그림이 생겨야 한다.

2.2 실제 데이터 전체 실행

.venv\Scripts\python.exe run_loeo.py --stage all

이 한 줄이 main, select, sensors, report를 순서대로 돈다. 기본 설정: 채널 5개, 창 [-2, 2] s, 10 Hz 저역통과 후 2배 다운샘플, 적격 기준 라벨 10개 이상과 클래스별 3개 이상, 예산 (0, 5, 10, 20)+최종, 오프셋 3, 시드 42, Gibbs 500+1500, 선택용 Gibbs 200+400.

2.3 스테이지를 나눠 실행하거나 중단 후 재개

.venv\Scripts\python.exe run_loeo.py --stage main
.venv\Scripts\python.exe run_loeo.py --stage select  --timestamp 20261001_090000
.venv\Scripts\python.exe run_loeo.py --stage sensors --timestamp 20261001_090000
.venv\Scripts\python.exe run_loeo.py --stage report  --timestamp 20261001_090000

select, sensors, report에서 --timestamp를 생략하면 같은 run_name 아래 가장 최근 폴더(folds/가 있는 것)를 자동으로 쓴다. 폴더가 여러 개라면 명시하는 편이 안전하다. main은 타임스탬프가 없으면 항상 새 폴더를 만든다.

폴드 결과는 끝나는 즉시 folds/<evaluator>*.json으로 저장되므로, 같은 --timestamp로 다시 실행하면 끝난 폴드는 건너뛴다. select와 sensors는 main이 저장한 <evaluator>_model.joblib(기준 모형과 파이프라인)를 재사용하므로 main을 먼저 돌리는 편이 빠르다.

2.4 설정 바꾸기

모든 Config 필드를 --set key=value로 덮어쓸 수 있다. 값은 Python 리터럴로 해석된다.

# 시드 3개로 반복, 예산 격자 변경
.venv\Scripts\python.exe run_loeo.py --stage main --set seeds="(42,43,44)" --set budgets="(0,2,5,10,20)"

# 특정 평가자만 held-out (디버그), GBT 베이스라인 추가
.venv\Scripts\python.exe run_loeo.py --stage main --set folds="('강신길','김진명')" --set gbt=True

# 선택 단계 정지 규칙에 쓰는 예산과 크기 격자
.venv\Scripts\python.exe run_loeo.py --stage select --timestamp ... --set sel_budgets="(0,10)" --set sel_sizes="(2,4,6,8,10,15,20,30)"

# 상관 임계값 민감도
.venv\Scripts\python.exe run_loeo.py --stage all --set rho_max=0.90 --set run_name=loeo_rho090
실행 시간 추정. 합성 데이터 측정치(population 7명, d 28, 약 700 에피소드에서 Gibbs 2000회 8 s)를 실데이터 규모(population 약 15명, d 약 40, 약 2500 에피소드)로 외삽하면 population 적합 1회에 30~50 s다. main은 폴드당 적합 3회(proposed, HB-full, 센서 PIP)와 베이스라인으로 3~5분, select는 projpred 경로 약 5분과 재적합 15회, sensors는 재적합 31회다. 폴드 15개 기준 전체 4~6시간을 예상한다. 시드를 3개로 늘리면 main이 그만큼 늘어난다.

4. 확인해야 할 점과 알려진 한계

  • population 구성. held-out 적격 기준(라벨 10, 클래스별 3)은 누구를 시험할지에만 쓰이고, population에는 라벨이 있는 모든 평가자가 들어간다. 클래스가 하나뿐인 평가자는 Population.fit이 자동으로 제외한다.
  • 센서 단위 PIP의 고착. 합성 데이터에서 센서 단위 spike-and-slab은 0 또는 1로 굳는 경향이 있었다. 그룹이 한 번 빠지면 slab 계수가 사전분포로 흘러가 재포함이 어렵기 때문이다. 실데이터에서도 그렇다면 sensors 스테이지의 전수 비교표를 주 근거로 쓰고 센서 PIP는 보조로만 쓴다.
  • 공통 판정 임계값 q_min. population 평가자가 적으면 between-evaluator 분산이 사전분포에 끌려 과대 추정되어 공통(common) 판정이 잘 나오지 않는다. 실데이터 U를 보고 q_min 0.9의 민감도를 함께 보고한다.
  • one-SE 규칙의 예산. 선택 점수는 sel_budgets(기본 0과 10)의 MLPD 평균이다. t = 0과 t = 10에서 순위가 뒤집힐 수 있으므로 두 예산 각각의 표도 함께 본다.
  • 선택 낙관 편향. 크기 k*는 모든 폴드의 held-out 점수로 정하므로 정수 하나에 대한 약한 낙관이 있다. 논문에는 이 점을 명시한다.
  • 재현성. 새 사용자 particle 시드는 폴드 시드와 오프셋에서 결정된다. 다중 체인 진단(Rhat)은 아직 자동화되지 않았고 fit_stats의 우도 trace만 저장된다.
